# 실시간 안내·다음 차량·출발지 접근 경로 수정 보고

기준 main: `769e592`. 작업 브랜치: `fix/next-vehicle-access-guidance-20261026`.
사용자 요청에 따라 main 병합과 운영 Worker 배포는 하지 않는다.

## 1. 확인한 원인

- 계산기가 다음 ETA가 없으면 `NEXT_ARRIVAL_UNAVAILABLE`, 다음 차량도 도보로 어렵다면
  `NO_CATCHABLE_TRAIN`으로 UNKNOWN을 반환했다. 첫 차량을 놓친다는 결정과 다음 ETA의
  존재가 결합되어 있었다.
- 서울 Worker의 노선 정규화는 `routeType`과 방향 표기가 없으면 행 전체를 제외했다.
  Android의 노선 연결도 유일한 공식 정류소·노선·순서가 있어도 카카오와 종착지 문구가
  다르면 실패했다. 마을버스 유형 2 자체는 기존에도 지원했다. 이 문제가 실제
  동대문01·273의 유일한 원인인지는 운영 응답을 확보하지 못해 확정하지 않았다.
- 지하철 분석은 실시간 열차와 시간표의 연결 증거가 없으면 종료했고, 위치 없는 공식
  시간표 대안이 없었다. 빈 응답은 화면의 분석 자체도 시작하지 못했다.
- 접근 경로는 도보 API가 NO_ROUTE를 반환한 뒤에만 검색했으며, 선택 후 실시간 안내를
  시작할 수 없는 참고 목록이었다.

## 2. 수정 파일

Android 경로는 `app/src/main/java/com/example/run_or_walk/` 아래다.

- `AutoGuidance.kt`: 다음 차량 상태·ETA 분리, 즉시 NEXT, 이후 차량 검토, 대기 상태 유지.
- `PaceNudgeComponents.kt`: 대기·예정시간·오류·앞선 차량 탑승 어려움 문구.
- `MainActivity.kt`: 접근 경로 선택·별도 화면 상태, 빈 응답 시간표 분석, ETA 표시 연동.
- `JourneyScreenState.kt`: 접근 안내 상태와 이전 이동 판단 보관.
- `AccessFallbackPolicy.kt`: 장거리 접근 선제 검색 조건.
- `BusBoardingResolution.kt`: 유일한 공식 노선 연결에서 선택 문구 차이 허용.
- `GyeonggiArrivalMatching.kt`: 다음 ETA의 원본 정밀도 보존.
- `SubwayTimetableAnalysis.kt`: 위치 대조 실패 시 명시적 시간표 기준 대안.
- `OfficialTimetableEstimation.kt`: 위치 기반 추정과 시간표만의 추정 출처 구분.
- `SubwayGuidanceSelection.kt`: 세 번째 이후 제공 차량 및 시간표 후보 전달.
- `SubwayArrivalHistory.kt`: 기기 내부의 예측·공식 도착 관측 비교 기록.
- `JourneyMonitoringService.kt`, `JourneyMonitoringController.kt`,
  `JourneyMonitoringAlertPolicy.kt`: 화면과 공통 판단, 재시도 중 대기 유지, 중복·놓칠 차량 알림 방지.
- `worker/src/bus-model.ts`: 선택 노선 메타데이터가 없어도 공식 ID·노선·순서 보존.
- 이 보고서.

## 3. 서울 버스 복구 범위

동대문01·273 이름의 정규화 재현에서 누락된 routeType·방향과 명시적 마을버스 유형을
확인했다. 같은 실제 정류소·노선·순서가 하나면 선택적인 종착지 표현 차이를 허용한다.
후보가 여럿이면 방향을 확인하며 ARS와 공식 stopId를 혼용하지 않는다.
근처 정류소 조회가 빈 결과이면 이름 검색도 시도한다. 서울 API 오류 메시지가 이전
경기 조회 메시지에 가려지지 않게 했다. 인증키 권한이나 운영 WAF 설정은 바꾸지 않았다.

## 4. 지하철 ETA

공식 양수 ETA를 먼저 사용하고, 다음으로 동일 열차·방향·정차 순서를 확인한 공식
위치+시간표 범위를 사용한다. 연결할 위치가 없으면 실제 운행일·방향·목적지 정차 순서가
맞는 향후 1시간의 공식 시간표를 별도 출처로 제시한다. 이것은 관측된 차량이나 신뢰 가능한
실시간 snapshot으로 만들지 않는다. 시간표 예측은 분 단위로 표시하며 30초마다 재평가한다.
이전 시간표의 제외 운행·노선·요일 범위는 기존 assets/timetables/README.md를 따른다.

## 5. 지정 출발지 접근

GPS와 지정 출발지의 거리를 계산해 30km 이상이면 도보 API 호출 전에 접근 대중교통을
탐색한다. 3km 초과의 장거리 보행에도 제안한다. 사용자가 경로를 선택하면 별도
JourneyScreenState에서 해당 경로의 실제 첫 승차점·공식 ETA·도보 계산·알림 기능을
재사용한다. 기존 출발지·목적지와 본래 선택 경로는 부모 상태에 남고 복귀 버튼을 제공한다.
접근 안내에는 기존 서울·경기·광역버스·지하철 연결을 사용하며 전체 환승 소요시간을
첫 차량 ETA로 해석하지 않는다. 접근 안내의 새 실시간 응답과 GPS는 복원 데이터로 저장하지 않는다.

## 6. 첫 차량 탑승 어려움

도보+여유시간으로도, 빠른 걸음+여유시간으로도 첫 차량을 탈 수 없으면 다음 ETA와
관계없이 NEXT_VEHICLE을 반환한다. 기존 빠른 걸음 판단 순서는 유지한다.
첫 두 차량 모두 어렵다면 대기를 유지하고, 공식적으로 제공된 세 번째 이후 ETA도 검토한다.
ETA가 없거나 만료된 차량의 도착시간을 임의로 생성하지 않는다.

## 7. 다음 ETA 수신 전후

| 상황 | 이동 판단 | 보조 안내 |
|---|---|---|
| 첫 차량 어려움, 다음 ETA 없음 | 다음 차량 대기 | 다음 도착예정시간 조회 중 |
| 여유가 있는 다음 ETA 수신 | 다음 차량 대기 유지 | 수신한 분/초 정밀도로 남은 시간 표시 |
| 다음 차량도 어려움 | 다음 차량 대기 유지 | 앞선 차량들 탑승 어려움·이후 차량 확인 |
| 다음 조회 오류 | 유효한 첫 ETA 또는 같은 장소의 확인된 놓침 판단 유지 | API 오류 표시 |
| 공식 막차·추가 운행 없음 확인 | 다음 차량 대기 | 추가 운행정보 없음 |

대기 판단 유지에는 같은 공식 승차 지점, 유효한 GPS·도보, 현재도 첫 차량 탑승이
어려움이 필요하다. 장소가 바뀌거나 위치·도보가 유효하지 않으면 판단을 다시 확인한다.

## 8. 백그라운드

서비스도 같은 계산기를 사용한다. 기존 30초 조회, 서버 Retry-After와 중복 알림 방지를
유지한다. 대기 중 놓칠 첫 차량에 ‘도착 임박’ 탑승 유도 알림을 보내지 않는다.
기존 진동 상태 게이트 재현에서 동일 판단의 반복 알림이 발생하지 않음을 확인했다.
실제 스마트폰의 화면 종료·절전 조건은 미검증이다.

## 9. 빌드·재현

Android compileDebugKotlin·assembleDebug, Worker TypeScript 검사·배포 dry-run을 실행했다.
저장소 외부 재현에는 요청서 10개 시나리오, 대기 유지와 다른 승차점 전환, 알림 중복,
접근 상태 분리, 동대문01·273 연결, 공식 1호선 위치·시간표 및 수인분당선 데이터가 포함된다.
최종 빌드가 성공했고 재현 36건이 통과했다(실패·오류 0건). Worker ETA 및 서울 노선 정규화 별도 재현도 통과했다. 기존에 삭제한 테스트
소스·의존성은 저장소에 복원하지 않았다.

## 10. 실제 API 확인

운영 Worker의 동대문·회기역 정류소 검색을 각 1회 실행했으나 모두 HTTP 403,
Cloudflare 1010으로 공식 데이터 도달 전에 차단됐다. 실제 동대문01·273 ETA 수신 성공이나
서울 인증키 복구를 확인했다는 뜻이 아니다. 기존 M5107 로직의 재현은 유지하되 이번
수정본으로 실제 M5107 운행을 확인하지 못했다. main 병합·운영 배포는 실행하지 않았다.
