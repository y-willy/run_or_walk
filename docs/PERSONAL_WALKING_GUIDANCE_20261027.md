## 실제 코드에서 확인한 변경 필요 부분

기존에는 GPS 속도 보정만 있었으며 걸음 센서와 별도 측정/저장 화면이 없었다. Foreground Service의 위치 요청이 ETA 요청과 같은 30초 루프 안에 있었고, 도보 경로 사이의 실제 진행도를 계산하지 않았다. 자동 안내는 개인 달리기 측정값 없이 기본 빠른 걸음 속도로 `뛰세요`를 표시했다. 화면의 기존 Urgency 진동 연결도 뛰기 3회·다음 차량 2회여서 이번 요구와 달랐다.

이미 main에 있던 열차 개별 선택, 조용한 새로고침, 지도 자동 배율 및 시간표 ETA를 중복 구현하지 않았다. 도착정보 선택은 실제 Compose 선택 컴포넌트를 다시 실행해 두 번째/세 번째/다음 페이지의 네 번째 열차 선택과 갱신 후 유지까지 검증했다.

## 계산 및 데이터 정책

- 보폭(cm) = 센서 걸음 수와 함께 유효했던 GPS 이동거리(m) / 해당 걸음 수 × 100.
- 평균 속도(km/h) = 유효 이동거리(m) / 유효한 실제 이동시간(s) × 3.6.
- 1km 예상시간(s) = 3600 / 평균 속도(km/h).
- 개인화 남은 도보시간(s) = ceil(실제 경로의 남은 거리(m) × 3.6 / 적용 걷기 속도(km/h)).
- 이동 가능 시간 = 선택 차량 도착 절대시각 − 현재 시각 − 안전 여유시간. 원본 ETA를 다시 차감하지 않는다.
- 걸어서 가능하면 WALK. 불가능하더라도 직접 측정해 저장한 달리기 속도로 계산한 시간이 충분하면 RUN. 그 시간도 부족하면 WAIT_NEXT.
- 달리기 속도가 없고 도보로는 부족하면 UNKNOWN으로 둔다. 기본 빠른 걸음 값을 달리기 속도로 간주하지 않는다. 측정한 달리기 값은 설정의 세부 설정에서 선택적으로 입력한다.
- 공식 실시간 ETA 우선, 없으면 기존 공식 위치+시간표/시간표 ETA 계산을 재사용한다. 추정 범위는 기존 정책대로 중간값으로 비교하며 분 단위 정밀도를 유지한다.
- 다음 차량 시간은 기존 공식 응답이나 유효한 공식 시간표에 실제로 있을 때만 사용한다.

GPS는 10초 이내, 정확도 20m 이내인 위치를 측정에 사용한다. 2~4초 GPS 선분을 모두 더하지 않고 8~15초 변위 구간과 최소 변위 기준을 사용해 흔들림 누적을 줄인다. 정지, 비정상 속도, 센서 걸음과 맞지 않는 이동, 오래된/역순 위치 및 긴 수신 공백을 제외한다. 센서 없는 경우에는 실제 GPS 속도/속도 정확도가 있는 구간만 속도 계산에 활용하고 걸음 수·보폭을 만들지 않는다.

속도 신뢰 조건은 100m 이상, 실제 이동시간 60초 이상, 유효한 보행 속도다. 보폭은 100걸음 및 센서와 짝이 맞는 거리 60m 이상이 추가로 필요하다. GPS 보폭을 정밀 실측으로 표현하지 않는다. 센서 초기값은 기준값으로만 사용하며 재부팅/카운터 역전 구간은 새 기준으로 시작한다.

측정은 분석 화면에서만 진행하고 화면 이탈/화면 꺼짐 시 일시정지한다. 저장하는 것은 요약 수치이며 측정 GPS 좌표열은 저장하지 않는다. 이동 안내의 화면 꺼짐 추적은 기존 위치 Foreground Service가 계속 수행하고 기존 60분 세션 제한을 유지한다.

## 경로 갱신·상태 전환·진동

- GPS 요청 초기 간격 4초, 최소 2초. 실제 전달 주기는 기기/절전 상태에 따라 달라질 수 있다.
- ETA는 기존 약 30초 폴링과 서버 Retry-After를 유지한다.
- 도보 API는 15초 이내 반복 요청을 막고, 90초 경과/원래 경로 출발점으로부터 60m 이동/경로 이탈 시 다시 요청한다. 조회 중 중복 요청을 만들지 않는다.
- API 사이에는 실제 경로 좌표에 투영한 GPS 진행도로 남은 거리와 도보시간을 갱신한다. 정지 중 시간만 흘렀다는 이유로 도보시간을 줄이지 않는다. 경로가 오래되거나 이탈하면 판단을 보류한다.
- 새 경로/승차점으로 이동하거나 종료할 때 위치·도보 Job을 취소하고 세션 번호를 바꾼다. ETA 및 도보 비동기 응답은 현재 세션/경로를 확인한 뒤 반영한다. 최신 GPS보다 오래된 응답은 위치를 덮어쓰지 못한다.
- 처음 유효한 상태는 조용히 설정한다. UI는 히스테리시스를 통과한 새 판단을 즉시 표시하고, 진동만 3초 이상 떨어진 연속 판정으로 확정한다. WAIT_NEXT → RUN, RUN/WAIT_NEXT → WALK 완화에는 기존 10초 여유를 유지한다.
- 확정 변경 시 WALK 1회 / RUN 2회 / WAIT_NEXT 3회, UNKNOWN 0회. 일반 진동 간격은 30초지만, 이전 확정 상태 및 직전 실제 진동보다 높은 긴급도는 예외로 알린다. 같은 긴급도 반복, 진동 OFF 및 쿨다운 중 완화는 조용히 상태만 반영한다. 새 승차 선택은 이전 진동 이력을 초기화하고 최초 상태를 조용히 설정한다.
- 알림 채널의 기본 진동과 수동 패턴이 중복되지 않게 안내 알림은 조용한 채널을 사용하고 위 패턴만 직접 재생한다. 기존 차량 도착 임박 알림 표시는 유지한다.
- 추적 중 메인 화면은 서비스가 확정한 assessment를 사용한다. 추적 전 두 검색 화면도 같은 계산기와 상태 필터를 사용한다.

## 최종 3항 검증 및 최소 수정 (2026-10-27)

### 1. 달리기 속도

자동 달리기 측정 화면은 없다. 기존 수동 입력이 있으며 경로는 `설정 → 안전 여유·기존 지도 시간 설정 → 직접 측정한 달리기 속도 (km/h · 선택) → 달리기 속도 저장`이다. 유한한 3~12km/h만 허용하고 빈 값은 설정을 해제한다. 사용자가 입력한 측정값이며 앱이 자동으로 검증한 달리기 실측값이라고 표현하지 않는다.

RUN은 위치·도보 경로·ETA가 유효하고, `ETA 잔여시간 - 여유시간 < 도보시간`이지만 `>= ceil(남은 거리 × 3.6 / 입력한 달리기 속도)`일 때다. 입력값이 없고 걷기로 부족하면 UNKNOWN이다. 기존 입력 기능으로 요구를 충족하므로 이번에 새 측정 기능을 추가하지 않았다.

실제 Compose 설정 화면에서 9.0 입력/저장/로컬 복원, 13.0 저장 차단, 빈 값으로 해제를 테스트했다.

### 2. 진동 제한 및 UI

수정 전 테스트로 아래 두 결함을 재현했다.

- RUN 진동 후 30초 이내의 확정 WAIT_NEXT가 3회 대신 0회 진동했다.
- 새 판단을 확인하는 최소 3초 동안 UI에도 이전 상태를 돌려줬다.

운영 코드 수정은 `MovementAdvice.kt` 한 파일이다. UI 표시와 진동 확인 대기를 분리했고, 긴급도 상승은 일반 30초 제한의 예외로 처리했다. 같은 제한 시간 안에서 이미 알린 긴급도가 반복되면 다시 진동하지 않는다. 예: WALK 1회 → RUN 2회 → WAIT_NEXT 3회는 각각 허용하고, 이후 RUN → WAIT_NEXT 반복은 다시 3회 울리지 않는다. 일반 완화 상태는 UI에 즉시 반영하지만 진동은 30초 제한을 유지한다. 최초/UNKNOWN/진동 OFF는 무진동이며 기존 완화 히스테리시스와 연속 판정 조건은 유지했다.

추가 테스트는 긴급도 상승, UI 즉시 반영, 같은 단계 반복 방지, 완화/진동 OFF/UNKNOWN, 새 승차 선택, 실제 서비스의 상태 게시 및 Vibrator 파형 전달을 검증한다. 서비스 검증은 Robolectric에 관측 이력을 주입해 수행한 것으로, 실제 휴대폰 진동 체감 검증은 아니다.
