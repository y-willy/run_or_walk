# 경기버스 경로 자동 연동 · 배포 및 실기기 확인

## 이번 기능이 하는 일

경로 모드에서 사용자가 카카오 추천 경로를 누르면 **첫 승차점의 지도 핀과 도보 접근 안내를 자동 지정**합니다. 별도로 지도에서 승차 장소를 골라야 진행되는 단계는 제거했습니다.

버스 경로는 다음 순서로 공식 실시간 데이터를 연결합니다.

1. 카카오 경로의 첫 BUS 구간에서 승차 정류장 이름·좌표·노선명을 읽습니다. **카카오 ID를 GBIS 공식 ID로 간주하지 않습니다.**
2. 경기도 공식 **주변정류소 목록조회**로 해당 좌표 인근의 후보 정류장을 검색합니다.
3. 위치가 100m 이내이고 정류장 이름이 정규화 후 일치하는 후보만 남깁니다. 최대 3개의 후보에 대해 **정류소 경유노선 목록조회**를 호출합니다.
4. 정류소 ID + 경유노선 ID + `staOrder`가 **정확히 한 개의 노선**으로 결정된 경우에만 공식 승차점을 연결합니다. 다른 노선에 동일 번호가 있거나 순번이 여러 개라면 자동 선택하지 않습니다.
5. 같은 공식 정류장에 대한 **버스도착정보목록조회**를 호출합니다. 선택한 노선·정류장 순번과 일치하는 데이터만 표시합니다. 관측 시각·차량 ID·ETA가 실제로 검증된 데이터만 뛰기/걷기 자동 판단에 사용합니다.
6. 경기도 매칭이 불가하면 기존 **서울 버스 공식 정류장** 연동을 시도합니다. 버스 서비스 미연결이더라도 첫 승차점·GPS·도보 경로는 가능한 범위에서 유지합니다.

지하철 경로도 선택만으로 첫 승차 위치를 자동 지정하고 공식 **역명+호선**의 단일 매칭을 시도합니다. 단, 제공된 경로에 탑승 방향 근거가 없거나 원본 도착정보가 오래됐으면 특정 열차를 임의로 선택하지 않습니다.

## 추가 승인·배포가 필요한 이유

기존 사용 승인 내용:
- `getBusArrivalListv2` 및 `getBusArrivalItemv2` — **도착정보 서비스**

이번 자동 정류장 매칭에 필요한 **다른 기능**:
- `getBusStationAroundListv2` — 주변 정류소 목록
- `getBusStationViaRouteListv2` — 해당 정류소 경유노선과 정류소 순번

경기버스정보 [주변정류소 문서](https://www.gbis.go.kr/gbis2014/publicService.action?cmd=mBusStationSearcharound), [경유노선 문서](https://www.gbis.go.kr/gbis2014/publicService.action?cmd=mBusStationRoute)를 참고하세요.

**기존 도착정보용 인증키만으로 정류소 조회 기능도 승인됐다고 가정하지 않습니다.** 공공데이터포털에서 해당 상세기능 접근 권한과 일일 한도를 확인한 뒤 기존 Worker의 Cloudflare **Secret**으로 설정합니다.

```sh
cd worker
npx --no-install wrangler secret put GYEONGGI_STATION_KEY
```

명령 뒤 나타나는 입력창에서 승인된 키를 입력합니다. 도착정보용 `GYEONGGI_BUS_KEY` 및 서울 지하철 `SEOUL_SUBWAY_KEY`는 그대로 유지합니다. 코드·`wrangler.jsonc`·APK·로그·채팅에 키를 넣지 않습니다. 같은 키로 두 서비스가 **모두 승인**됐다면 계정에서 서비스별 권한을 확인한 뒤 동일한 값을 별도 Secret에 등록할 수 있습니다.

**반드시 기존 `run-or-walk` Worker가 있는 Cloudflare 계정에서** `whoami`와 기존 Durable Object migration 이력 및 namespace 충돌을 확인하고 `npm run deploy`하세요. GitHub 푸시만으로 Worker의 새 경로가 서비스에 반영되지는 않습니다. 기존 서명 APK도 소스 푸시만으로 자동 업데이트되지 않습니다.

새 API는 기존 `GyeonggiBusCoordinator`의 **같은 글로벌 SQLite 900건/24시간 호출 장부**를 사용합니다. 정류장 주변 조회, 경유노선 조회, 도착정보 조회 각각의 원본 호출 1건을 차감하며 자동 재시도하지 않습니다. 기존 캐시·동시 조회 병합과 10초 오류 backoff를 유지합니다. 다른 Worker의 동일 키 사용량은 집계하지 않습니다.

## 검증 결과 · 2026-10-25

격리된 feature 브랜치 복제본에서 실행:
- `npm run check`: 통과
- `npm test`: **203개 통과**, 실패 없음
- `npm run build`: Wrangler **dry-run** 통과. 실제 배포 아님.
- Android `:app:compileDebugKotlin`: **통과 확인 불가**. 이 환경은 Gradle 9.6 배포본 다운로드가 네트워크 제한으로 중단됐으며 Android SDK도 확보하지 못했습니다.

위 테스트는 모의 API 응답에 대한 Worker 코드 검증일 뿐, 실제 경기버스 제공자의 승인된 키로 5100번·3번 도착정보가 확보됨을 입증하지 않습니다.

## 스마트폰 확인 순서

1. Android Studio에서 `feature/run-or-walk-navigation` 브랜치를 받아 Kotlin 컴파일·단위 테스트·APK 빌드를 수행하고 **그 새 APK를 설치**합니다.
2. Cloudflare 기존 Worker 배포 후 `/health`와 경기버스 `/gyeonggi/bus/nearby?x=...&y=...`를 **소량** 점검합니다. API 키를 URL에 넣지 않습니다.
3. 수원 영통/망포의 5100번, 3번을 포함한 경로를 검색해 한 경로를 선택합니다. 첫 승차점이 자동으로 지도에 표시되고 도보 접근이 갱신되는지 확인합니다.
4. GBIS 정류소·노선·`staOrder` 매칭이 확인될 때만 해당 버스의 도착 예정정보가 표시되는지 봅니다. 중복 노선, 불명확한 승차 방향, 부정확한 응답에서는 자동 뛰기/걷기 판단이 보류되어야 합니다.
5. 수인분당선 영통·망포역은 공식 역명·호선 매칭까지 자동 진행되는지 확인합니다. 출발 방향이 제공되지 않으면 차량 선택은 보류될 수 있습니다.
6. 역·노선을 빠르게 바꾸거나 위치 갱신 중에 이전 요청이 덮어쓰지 않는지 확인합니다.

실기기 GPS, 제공자 인증·승인, 실제 운행 데이터 정확도 및 화면 꺼짐 **경기버스 안내**는 아직 현장 검증하지 않았습니다. 경기버스 자동 연결은 화면이 활성화된 동안만 동작하도록 제한하며, 화면 꺼짐 서비스가 경기버스 공식 ID를 지원한다고 가정하지 않습니다.
