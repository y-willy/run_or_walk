# 공식 실시간 도착정보 API 조사

조사일: 2026-10-25 (한국 시각). 범위: **서울 지하철 우선**, 경기도 확장은 확인 후 결정. 이 문서는 조사 결과다. 이후 사용자가 HTTPS 중계 방식과 배포 코드 준비를 선택했으며, 실제 공개 서버와 전용 키는 아직 준비되지 않았다. 이 조사에서 공식 역 목록과 공개 응답을 로컬 자료로 저장했으며, 인증키를 읽거나 인증 요청을 보내지 않았다. 공개 문서, 공식 역 목록 파일, 공개 `sample` 응답만 확인했다. 연동 코드의 현재 승인·구현 상태는 별도로 확인해야 한다.

## 권장 제공기관과 범위

서울특별시 TOPIS의 **서울시 지하철 실시간 도착정보** (`OA-12764`, `realtimeStationArrival`)가 우선 후보이다. 버스 데이터는 이 서비스에 포함되지 않는다.

- [공식 데이터셋](https://data.seoul.go.kr/dataList/OA-12764/A/1/datasetView.do)
- [공식 요청·응답 명세](https://data.seoul.go.kr/dataList/openApiView.do?infId=OA-12764&srvType=A)
- [인증키·사용량 안내](https://data.seoul.go.kr/together/guide/useGuide.do)
- 이용허락: 공공누리 1유형, 출처표시; 상업적 이용 및 변경 가능. 앱에 제공기관과 출처를 표시해야 한다.

**지역 제한은 역별로 검증해야 한다.** 데이터셋 본문에는 “서울시 이외의 역구간은 미제공”이라는 안내와 광명·서동탄·춘천 예시가 있다. 한편 같은 데이터셋의 최신 역 목록에는 수원·기흥·망포 등 경기도 역도 포함된다. 목록에 있다는 사실만으로 실시간 도착정보가 제공된다고 보장할 수 없다. 따라서 서울을 기본 지원 범위로 삼고, 경기도는 승인된 인증키로 실제 대상 역·호선·방향을 확인한 후 확장하는 것이 적절하다. 현재 경기도의 실제 도착 응답은 미검증이다.

## 요청 경로와 HTTPS 확인 결과

공식 명세의 경로는 다음과 같다. 역명은 하나의 URL 경로 요소로 인코딩해야 한다.

```text
http://swopenAPI.seoul.go.kr/api/subway/{KEY}/json/realtimeStationArrival/{START_INDEX}/{END_INDEX}/{statnNm}
```

필수 인자: 발급받은 `KEY`, `TYPE` (`json`/`xml` 등), 서비스명 `realtimeStationArrival`, 시작·종료 위치, **제공기관 표기와 일치하는 역명** `statnNm`. API는 역명으로 요청하므로, 내려받은 공식 역 목록의 ID는 응답을 검증하고 호선별 결과를 선택하는 데 사용한다. 공식 예제는 `/0/5/서울`이다. 샘플키는 서울역만 조회할 수 있으며 최대 5개 결과만 허용된다. 일반 요청은 한 번에 최대 1,000건이다.

현재 조사 환경에서 관측한 결과:

| 요청 | 관측 결과 | 판단 |
| --- | --- | --- |
| 공식 HTTP 호스트의 공개 `sample` 서울역 요청 | HTTP 응답에 정상 JSON, `INFO-000`, `realtimeArrivalList` 반환 | 공개 샘플의 경로와 JSON 형태 확인 |
| `https://swopenapi.seoul.go.kr:443/api/subway/...` | 환경 프록시의 HTTP 503, upstream connection timeout | HTTPS 동작 확인 실패; 제공기관의 HTTPS 미지원으로 단정할 수는 없음 |
| 일반 정적 API의 `https://openapi.seoul.go.kr:8088/...` | upstream TLS wrong version | 문서의 HTTP 포트를 HTTPS로 바꾸는 것으로 해결되지 않음 |

**앱이 공식 API에 HTTPS로 직접 연결할 수 있다는 근거는 아직 확보하지 못했다.** 공개 문서에도 조사한 API 경로는 HTTP로 표기되어 있다. 연동 전에 제공기관의 지원 HTTPS 주소를 확인하거나 별도 HTTPS 중계 서버 운영 여부를 결정해야 한다. HTTPS 검증 실패를 이유로 앱의 전역 cleartext 허용이나 TLS 검증 해제를 도입하면 안 된다. HTTP 키 전달 여부나 중계 서버 운영은 사용자가 검토할 구체적인 도입 조건이다.

## 실제 JSON과 필요한 응답 필드

공개 `sample` 응답은 다음 구조였다. 일반 명세의 `RESULT.CODE` 표기와 달리 실제 JSON의 상태는 `errorMessage.code`에 있었다. 구현 시 실제 JSON 구조를 기준으로 서비스 오류와 빈 결과를 구분해야 한다.

```json
{
  "errorMessage": {"status": 200, "code": "INFO-000", "total": 19},
  "realtimeArrivalList": [
    {
      "subwayId": "1004",
      "updnLine": "상행",
      "trainLineNm": "불암산행 - 회현방면",
      "statnId": "1004000426",
      "statnNm": "서울",
      "btrainSttus": "일반",
      "barvlDt": "330",
      "btrainNo": "4302",
      "bstatnId": "1004000409",
      "bstatnNm": "불암산",
      "recptnDt": "2026-10-25 06:09:50",
      "arvlCd": "99"
    }
  ]
}
```

위 값은 조사 시 공개 샘플에서 관측한 한 행의 발췌이며 현재 도착을 의미하지 않는다. 필드의 숫자처럼 보이는 값도 문자열로 반환된다. 열차번호에는 `0004`나 `A2007` 같은 값이 실제로 있으므로 정수로 변환하면 안 된다.

전체 공개 샘플 5행은 `app/src/test/resources/seoul_public_sample_arrivals_20261024.json`에 원래 응답 구조로 저장했다. 출처는 위 공식 명세의 `sample` 서울역 요청이며, 재배포 근거는 데이터셋의 공공누리 1유형 출처표시 조건이다. 테스트 전용 고정 응답으로 사용하며 사용자에게 현재 도착정보로 표시하면 안 된다. 요청에 사용된 것은 공개 문자열 `sample`뿐이며 실제 인증키는 없다.

| 필드 | 공식 의미 | 사용 시 주의 |
| --- | --- | --- |
| `subwayId` | 호선 ID | 동일 역명의 환승 호선을 구분 |
| `statnId`, `statnNm` | 도착 대상 역 ID·역명 | 선택한 탑승역과 일치하는지 검증 |
| `updnLine` | 상행/내선 또는 하행/외선 | 표기만으로 모든 분기·회차 방향을 확정할 수 없음 |
| `trainLineNm` | 종착역행 및 다음 역 방면 설명 | 승객용 방향 설명; 문자열 하나만으로 ID를 대체하지 않음 |
| `statnFid`, `statnTid` | 이전·다음 지하철역 ID | 노선 그래프 및 다음 역과 함께 방향 확인 |
| `bstatnId`, `bstatnNm` | 종착역 ID·이름 | 단축 운행·분기 노선을 구분 |
| `btrainNo` | 운행 중인 호선별 열차번호 | 호선·운행일·방향 등과 함께 식별; 전역 고유 ID 아님 |
| `btrainSttus` | 일반·급행·ITX·특급 | 경로에서 요구한 열차 종류와 맞는지 확인 |
| `barvlDt` | 도착예정시간, **초** | 0을 곧바로 “지금 탈 수 있음”으로 해석하지 않음 |
| `recptnDt` | 도착정보를 생성한 시각 | 데이터 생성 이후 경과 시간과 신선도 확인 필요 |
| `arvlCd` | 0 진입, 1 도착, 2 출발, 3 전역출발, 4 전역진입, 5 전역도착, 99 운행중 | 이미 출발한 열차를 탈 수 있는 후보로 취급하지 않음 |
| `arvlMsg2`, `arvlMsg3` | 도착·위치 메시지 | 사용자 설명 보조; 구조화 필드를 대체하지 않음 |
| `ordkey` | 방향·순번·거리·종착역·급행 여부를 포함한 순서 키 | 안정적인 열차 고유 ID로 간주하지 않음 |
| `lstcarAt` | 막차 여부, 1/0 | 마지막 열차 관련 안내에 사용 가능 |

공식 데이터셋은 수집·가공 시차가 있을 수 있으므로 `recptnDt`와 현재 시각의 차이를 반영하라고 안내한다. ETA를 계산할 경우 도착예정 초에서 생성 이후 경과 시간을 반영하고, 오래된 응답·미래 시각·누락·파싱 실패는 별도 상태로 처리해야 한다. 같은 공개 샘플에도 `barvlDt=0`이면서 `arvlCd=2`(출발)인 행이 있으므로, ETA 숫자만으로 판단하는 것은 안전하지 않다. 임의의 양수 대기시간을 만들어 표시해서도 안 된다.

샘플의 `recptnDt`는 `yyyy-MM-dd HH:mm:ss` 형태이며 UTC 오프셋이 없다. 관측 값은 한국 현지 시각과 일치했지만, 이번에 확인한 공식 필드 설명에는 시간대가 명시되어 있지 않았다. `Asia/Seoul`로 해석하는 경우 이를 구현 가정으로 기록하고 운행 검증 시 확인한다. `arvlCd=0/1`은 진입·도착 상태이며 탑승 가능 시간을 보장하지 않는다. `barvlDt=0`은 샘플에서 도착·출발·운행중 상태 모두에 나타나므로 모든 경우를 숫자 0초 도착으로 합치면 안 된다.

서비스 상태는 최소한 정상 `INFO-000`, 데이터 없음 `INFO-200`, 유효하지 않은 키 `INFO-100`, 요청 오류, 서버 오류를 구분한다. HTTP 200만으로 데이터 성공으로 판정하지 않는다. 선택한 호선·탑승역·방향·열차 종류가 확정되지 않은 경우 실시간 탑승 추천을 만들지 않는다.

## 역 ID, 역명과 Kakao 검색 결과 연결

[해당 공개 파일 내려받기](https://datafile.seoul.go.kr/bigfile/iot/inf/nio_download.do?infId=OA-12764&infSeq=2&seq=57&useCache=false)

다운로드한 자료를 `app/src/main/assets/seoul_subway_stations.json`에 저장했다. 파일 날짜는 **2026-09-02**, 조회일은 **2026-10-24**, 제공기관은 **서울특별시 TOPIS**, 이용허락은 데이터셋의 **공공누리 1유형(출처표시)**이다. 각 행의 `stopId`는 `STATN_ID`, `routeId`는 `SUBWAY_ID`, `name`은 `STATN_NM`, `lineName`은 `호선이름`이며 모두 원문 문자열이다. `routeId/stopId/name/lineName`으로 정렬하고 중복을 검사했다. 원본 696행 모두 보존했으며 좌표는 추가하지 않았다. 이 자료는 이름·호선별 식별 목록이며, 해당 역의 실시간 제공 여부나 검증된 플랫폼 좌표를 증명하지 않는다.

### 외부 코드와 실시간 ID는 다른 이름공간

[서울교통공사 노선별 지하철역 정보 OA-15442](https://data.seoul.go.kr/dataList/OA-15442/A/1/datasetView.do)의 [`SearchSTNBySubwayLineInfo` 명세](https://data.seoul.go.kr/dataList/openApiView.do?infId=OA-15442&srvType=A)는 `STATION_CD`(전철역코드), `STATION_NM`, `LINE_NUM`, `FR_CODE`(**외부코드**) 등을 제공한다. 소개된 범위도 서울교통공사 1~8호선과 9호선 2~3단계이다. `FR_CODE`나 이 API의 `STATION_CD`를 TOPIS의 `STATN_ID`와 동일시하거나 접두사를 붙여 생성하면 안 된다. 실시간 역 목록의 실제 ID를 사용한다.

[Kakao Local 공식 문서](https://developers.kakao.com/docs/latest/ko/local/dev-guide)에 따르면 검색 결과 `id`는 **장소 ID**이며, `place_name`, 주소, `x`(경도), `y`(위도), `category_group_code` 등을 제공한다. 지하철역 그룹은 `SW8`이다. 이 문서는 Kakao 장소 ID와 TOPIS 실시간 역 ID의 공통 키를 제공하지 않는다.

권장 연결 절차:

1. Kakao 장소 ID는 장소 검색의 ID로 보존하고, 실시간 ID는 제공기관 이름과 함께 별도 필드로 저장한다.
2. 공식 역 목록을 기준으로 역명 별칭을 관리한다. 예를 들어 Kakao의 `서울역`과 실시간 명세의 `서울`은 명시적 별칭으로 연결할 수 있다. 임의로 모든 이름에서 마지막 `역`을 제거하거나 괄호를 모두 지우지 않는다. `신촌`과 `신촌(경의중앙선)`처럼 구분이 필요한 경우가 있다.
3. 출발역 **호선**을 함께 확정한다. 서울역 같은 환승역은 이름 하나로 특정 `statnId`를 결정할 수 없다. 첫 탑승 호선·다음 역·목적지 방면이 없는 경로라면 추가 선택 또는 확인이 필요하다.
4. 동일 이름·후보가 여럿이면 검증된 주소·좌표 자료와 호선 정보를 사용해 후보를 좁힌다. 공개 실시간 역 목록 파일에는 좌표가 없으므로 이 파일만으로 좌표 검증이 완료됐다고 표시하지 않는다. 모호한 경우 자동으로 가장 가까운 후보에 연결하지 않는다.
5. 요청에 공식 `STATN_NM`을 사용하고, 응답에서 `subwayId + statnId`를 확인한 뒤 다음 역·종착역·방향·열차 종류로 후보를 거른다. 선택된 역 하나의 도착시간을 다른 역까지의 대기시간으로 사용하지 않는다.
6. 검증한 대응표에는 데이터 버전과 검증 근거를 남기고 재사용한다. Kakao 검색 좌표만으로 플랫폼 승차 위치까지 검증되었다고 표시하지 않는다.

현재 앱의 `KakaoTransitChoice`에는 서비스명과 탑승 정류장명은 있지만, 공식 지하철 호선 ID·역 ID·다음 역·방향을 확정할 구조가 없다. 외부 API를 붙이기 전에 경로 제공 응답의 실제 계약과 이 정보를 어떻게 확보할지 검토해야 한다.

## 인증키 발급·사용량·사용자가 준비할 것

공식 이용안내에는 일반 인증키와 **실시간 지하철 인증키 신청**이 구분되어 있다. 서울시 로그인 후 실시간 지하철용 인증키를 신청해야 한다. Kakao 키나 일반 서울 정적 API 키가 대체한다고 가정하면 안 된다.

- 공식 안내의 실시간 지하철 기본 한도: **하루 최대 1,000회 요청**.
- 한 번의 응답 최대 1,000행은 하루 호출 한도와 별개이다.
- 한도 완화 안내: 활용사례(갤러리)에 인증키와 콘텐츠 등록. 자동 승인, 무제한 보장, 즉시 반영, 추가 비용 여부를 이 안내만으로 확정할 수 없다.
- 초당 한도, 정확한 한도 집계 범위·초기화 시각·운영 SLA·증설 후 수치는 이번 공개 문서에서 확인하지 못했다.
- 30초마다 요청하면 한 클라이언트가 1,000회를 약 8시간 20분 만에 사용한다. 여러 사용자·역의 요청은 별도 예산이 필요하다. 가시 화면에서만 조회하고, 중복 요청 병합·캐시·오류 재시도 제한·백오프를 설계해야 한다.
- 사용자는 도입 승인 전에 실시간 지하철 키 발급 가능 여부, 지원할 서울 역·호선, HTTPS 직접 연결 또는 중계 서버 운영 방식을 결정해야 한다. 키는 채팅·문서·로그·저장소에 넣지 않고 승인된 비밀값 설정 경로로 전달해야 한다.

## 버스는 추후 별도 검토

현재 지하철 우선 범위에는 버스 연동을 포함하지 않는다. 후속 후보는 [서울 버스도착정보조회](https://www.data.go.kr/data/15000314/openapi.do), [경기도 버스도착정보 조회](https://www.data.go.kr/data/15080346/openapi.do), [국토교통부 TAGO 버스도착정보](https://www.data.go.kr/data/15098530/openapi.do)이다. 각 서비스별 활용신청·정류장 ID·지원 지역을 별도로 확인해야 하며, TAGO의 실제 지원 도시는 도시코드 목록 오퍼레이션으로 확인해야 한다. 공개 포털 표기 개발 트래픽은 서울·경기도 각각 1,000, TAGO 10,000이다. 운영 한도는 활용사례 등록 후 증설 신청 가능이라고만 안내되어 있어 승인 수치를 보장할 수 없다.
