# 현위치 → 지정 출발지 파란 경로 표시 수정

기준 main `4cede9a`, 작업 브랜치 `fix/map-gps-departure-path-20261030`.

## 코드에서 확인한 누락·가림 조건

- `KakaoMapPanel`은 지정 출발지가 있으면 별도 `accessSegments`만 파란색으로 그린다. 이미 수신한 `walkingPoints`만으로는 이 선이 표시되지 않는다. 그런데 기존 재사용 조건은 끝점 20m 이내를 별도로 요구해, 기존 도보 계산기에서 정상 승인한 요청 연결/도로 보정 좌표도 재사용하지 못했다.
- 기존 `walkingMapViewportPoints`는 승차점이 있으면 모든 접근 경로 좌표를 무시하고, 현위치와 승차점 및 승차점까지 도보 경로로만 지도 범위를 계산했다. 파란 경로의 굽은 구간이나 지정 출발지가 화면 밖에 놓일 수 있었다.
- 파란 선과 초록 선은 같은 z-order와 폭으로 파란 선부터 그려졌다. 겹치는 구간에서는 초록 선이 파란 선을 가릴 수 있었다.
- 현위치 → 출발지 조회의 `LaunchedEffect`가 최종 목적지와 본 경로의 변경에도 취소됐다. 아직 파란 좌표가 준비되지 않은 시점이면 불필요한 취소/재시도 대기가 발생할 수 있었다.

사용자의 휴대폰 화면과 원래 선택 좌표를 직접 캡처한 것은 아니다. 위 조건은 실제 코드와 재현 테스트에서 확인한 것이며, 어느 하나를 사용자 기기에서의 유일한 원인으로 단정하지 않는다.

## 수정

- `MainActivity.kt`: 접근 경로 조회를 지정 출발지/접근 경로 선택에만 연결. 이미 받은 실제 도보 경로를 공유 검증 규칙으로 재사용. 다른 출발지의 이전 접근 선은 지도에 전달하지 않는다.
- `WalkingAccessPolicy.kt`: 실제 접근 경로 전체와 현위치·출발지·승차점을 카메라 범위에 포함한다. 선 표시 계획에서 초록 12px/z10000, 파랑 8px/z10001을 사용한다. 겹쳐도 파란 선과 초록 테두리를 함께 볼 수 있게 한다.
- `reuseWalkingForMapAccess`: 원래 요청의 출발/도착 연결, 위치·경로 신선도, GPS 이동 범위를 확인한다. 기존 120초 도보 유효기간과 원본 수신시각을 유지하며 새 수신으로 취급하지 않는다. 지도 전용 경로를 다른 승차점의 도보 판단으로 전용하지 않는다.
- `kakaomapkanel.kt`: 위 좌표·색상·폭·z-order를 실제 Kakao SDK RouteLineOptions에 적용한다. 기존 사용자 카메라 조작 보존 및 ETA 갱신 때 재조회/자동 리셋하지 않는 정책을 유지한다.
- `MapDeparturePathRegressionTest.kt`: 지도 범위, 경로 겹침, 정상 도로 보정 좌표 재사용, 만료/다른 출발지/먼 GPS 제외, 정류장 단독 지도 보존 등 7건.

실제 API의 좌표를 그대로 사용한다. 좌표가 없을 때 임의의 직선이나 가짜 연결 구간을 만들지 않는다.

## 실제 API 및 모의 데이터 검증

[실제 API 결과](validation/map-departure-20261030/live-api-proof.txt): 2026-10-30 01:19 KST.

- 공개 장소 종각역 1호선 → 종로2가.삼일교 → 강남역 2호선.
- 실제 도보 API: 588m, 557초, 실제 경로 좌표 25개.
- 실제 대중교통 API: N37(심야), 초록 경로 구간 1개.
- 수정 코드에서 파란 구간 1개와 초록 구간 1개 생성, 파란 좌표 전부 카메라 범위에 포함, 파란 z-order가 초록보다 높음, 원본 경로 좌표 변경 없음 확인.
- GPS 입력은 공개 종각역 위치를 사용한 모의 입력이다. 별도 프로브는 기본 테스트에 포함하지 않으며, 단위 테스트는 모의 좌표로 실행한다.
- 실제 휴대폰 Kakao SDK의 최종 화면/제스처/화면 회전 렌더링은 아직 확인하지 않았다.

## 기존 UI 테스트의 시계 수정

초기 전체 회귀 실행에서 기존 `GuidanceRevisionUiTest.validLiveDataOverridesAnOldUnknownMonitoringAssessmentImmediately` 1건이 실패했다. 진단 로그에서 모의 GPS의 벽시계 시각이 UI의 단조 시계 기반 시각보다 102ms 미래여서 `LOCATION_UNAVAILABLE`이 된 것을 확인했다. 이 테스트의 입력만 `vm.displayClock.now()`에 맞췄다. 실제 앱의 위치 유효성 기준이나 이동 판단 계산식은 변경하지 않았다. 진단용 임시 출력은 제거했다.
